# 구현 계획 (Plan)

한국후지필름형 정기 설문 폐루프 에이전트의 구현 계획입니다. 범위의 근거는 [mvp.md](mvp.md), 요구사항은 [prd.md](prd.md), 구현 계약은 [spec.md](spec.md)입니다. 이 문서에는 코드가 없고, 단계(Phase)별로 무엇을 만들고 어떻게 확인하는지만 적었습니다.

## 표기 규칙

| 표기 | 의미 |
| --- | --- |
| 결정 | 사용자가 정했거나 prd.md·spec.md에서 이미 결정된 내용 |
| 가정 | 계획을 위해 둔 값. 출처 없음 |
| 설계 제안 | 승인 전까지 확정이 아닌 제안 |
| 확인 필요 | 값이나 사실을 모르는 항목. 7절 목록에 PQ 번호로 모았다 |
| 실측 | 실제 데이터에서 센 값 |

- 이 문서의 소요 시간은 모두 **가정**입니다. 근거가 없고, AI 도구 사용을 반영하지 않은 1인 작업 시간(시간 단위)입니다. 사용자가 AI 도구 기준으로 세운 별도 추정이 있고 5절에서 비교합니다(확인 필요 PQ-8).
- Git 저장점은 태그 이름으로 적었습니다. 이 프로젝트는 아직 git 저장소가 아니라서 Phase 0a에서 저장소를 만듭니다. 저장점은 사용자가 요청할 때만 만들고, 요청 없이 커밋하지 않습니다.
- 확인 방법은 브라우저와 Supabase 화면, 터미널에서 사용자가 직접 할 수 있는 것만 적었습니다.

## 1. 전제와 Phase 번호

- Phase 번호는 prd.md와 spec.md가 인용한 노션의 번호에 맞췄습니다: **Phase 0**은 데이터 적재, **Phase 3**은 광고성 판정 파일럿, **Phase 6**은 폐루프 한 번 완주(회차 리포트 출력). 나머지 번호(1, 2, 4, 5, 7, 8, 9)는 이 문서에서 새로 붙였습니다. 사용자가 전달한 노션 Phase(5.2절)와 번호와 내용이 다릅니다. 예를 들어 노션 Phase 7은 대시보드·근거 뷰어·검증 페이지이고, 이 문서의 Phase 7은 n8n 연결입니다(확인 필요 PQ-3).
- 데이터 적재는 Phase 0a(환경), 0b(리뷰), 0c(설문과 합성 응답), 0d(네이버 글)로 쪼갰습니다.
- 담당자 업로드 화면과 사람 검토 단계는 MVP에서 제외했으므로(prd.md 7절) 계획에도 없습니다.
- SP-1(`GET /api/health`)은 승인 대기라 계획에 넣지 않았습니다. 서버 확인은 FastAPI의 `/docs` 화면으로 합니다.

## 4. Phase 상세

### Phase 0a: 환경 준비

**만드는 것**
- git 저장소 초기화. `.gitignore`에 `database/data/`(원본 CSV·합성 응답 결과)를 추가한다(spec.md SQ-11, 결정).
- backend 골격: FastAPI 실행, 환경 값 읽기, `.env.example`.
- frontend 골격: Vite + React(JavaScript)가 5173 포트에서 열림.
- SQLAlchemy + Alembic 설정(spec.md 1절, 결정), psycopg 3, `backend/.venv`, pytest 1개.
- Supabase 연결(`DATABASE_URL`, session pooler 방식).

**완료 확인 기준**
1. backend 서버를 켜고 브라우저에서 `http://localhost:8000/docs`가 열린다.
2. frontend를 켜고 브라우저에서 `http://localhost:5173`이 열린다.
3. 터미널에서 pytest를 실행하면 전부 통과한다(SQLite로 돈다).
4. DB 접속 확인을 실행하면 Supabase에 연결됐다는 결과가 나온다.
5. `git status`에 `.env`는 보이지 않고 `.env.example`은 보인다.

**예상 소요** 4시간(가정) **선행** 없음. Supabase 프로젝트와 `DATABASE_URL`이 준비되어 있어야 한다(확인 필요 PQ-9) **저장점** `phase-0a-scaffold`

### Phase 0b: 리뷰 적재

**만드는 것**
- `product`, `review` 테이블(spec.md 3.2절)과 마이그레이션.
- 쿠팡 CSV(`database/data/`에 복사해 둔 파일)를 읽어 적재하는 스크립트. `author`, `seller`, `source_file`, `original_no`는 읽지 않고, 빈 문자열은 NULL로 바꾼다(spec.md 3.1절).

**완료 확인 기준** (Supabase의 Table Editor에서)
1. `review` 행이 1,302개, `product` 행이 3개다.
2. `title`이 NULL인 행이 1,152개, `review_text`가 NULL인 행이 1,005개, `variant`에 값이 있는 행이 351개다 (모두 실측).
3. `rating`별 건수가 5점 1,164 / 4점 91 / 3점 25 / 2점 4 / 1점 18이다 (실측).
4. `review_id`의 최솟값이 1043, 최댓값이 2344다 (실측).
5. `review` 테이블에 `author` 열이 없다.
6. 적재 스크립트를 두 번 실행해도 `review` 행이 1,302개로 그대로다.

**예상 소요** 4시간(가정) **선행** 0a **저장점** `phase-0b-reviews-loaded`

### Phase 0c: 설문 구조와 합성 응답 적재

**만드는 것**
- `round`, `survey_question`, `survey_response`, `survey_answer` 테이블.
- KOSSDA 변수 구조를 따른 문항 정의와, G2에서 정한 건수·회차 수의 합성 응답 생성기(라벨 고정).
- 합성 응답 적재 스크립트. 합성 응답에는 `is_synthetic`이 항상 참이다(DR-2).

**완료 확인 기준** (Table Editor에서)
1. `survey_response`의 행 수가 G2에서 정한 합성 건수와 같고, `is_synthetic`이 거짓인 행이 없다.
2. `round`의 행 수가 G2에서 정한 회차 수와 같다.
3. `survey_question`에서 문항 수와 문항 유형이 정한 구조와 맞다.
4. `survey_response`의 `family_id`가 모두 NULL이다(공통 설문, spec.md SQ-5 기본안).
5. 생성기를 두 번 실행해도 행이 중복으로 늘지 않는다.

**예상 소요** 8시간(가정) **선행** 0a, G2 **저장점** `phase-0c-survey-synthetic`

- 이 단계는 KOSSDA 한국 응답자(15683의 500명, 14488의 234명)를 실제로 적재하는지, 구조만 참고하는지가 문서마다 다르게 읽힙니다(확인 필요 PQ-4). 위 기준은 합성만 적재한다고 가정했습니다.
- 합성 응답에서 나온 수치는 성과로 쓰지 않습니다(prd.md).

### Phase 0d: 네이버 글 수집·적재 (컷 후보)

**만드는 것**
- 네이버 블로그·카페 글 수집과 적재. 쿠팡 본문이 297건(실측)뿐이라 보강하는 외부 VOC입니다.

**완료 확인 기준**
1. 적재된 글의 건수가 수집 보고와 같다. 건수는 수집 후 측정한다(목표값 없음).
2. 글마다 출처가 쿠팡이 아니라 네이버로 구분된다.
3. 비밀 값(앱 키)이 저장소에 없다(`git status`와 `.env.example` 확인).

**예상 소요** 6시간(가정) **선행** 0a. 네이버 글의 열 구성과 테이블이 정해져야 한다(spec.md SQ-12). 앱 등록 작업은 시작 전이다 **저장점** `phase-0d-naver-loaded`

### Phase 1: 읽기 API와 오류·로그 기반

**만드는 것**
- 제품군 시드(G1), A-1(제품군 목록), A-2(회차 목록), A-4의 리뷰 근거 조회.
- 오류 응답 형식(400·404·422·500), `request_id`, JSON 로그(7절).

**완료 확인 기준** (`/docs` 화면에서 실행)
1. `GET /api/families`가 G1에서 정한 제품군 목록을 돌려준다.
2. `GET /api/rounds`가 G2에서 정한 회차 목록을 돌려준다.
3. `GET /api/evidence/review/1043`의 응답에 `rating`, `date`, `review_text`가 있고 `author`, `variant`는 없다.
4. 제목만 있는 리뷰 하나를 조회하면 `review_text` 자리에 제목이 들어가고 `text_source`가 `title`이다(spec.md SQ-15 기본안).
5. 없는 ID를 조회하면 404, 숫자가 아닌 ID나 종류가 틀린 경로는 422이고, 모든 오류 응답에 `request_id`가 있다.
6. `backend/logs/`에 로그 파일이 생기고, 열어서 검색하면 리뷰 본문과 키 문자열이 없다.
7. pytest가 전부 통과한다.

**예상 소요** 5시간(가정) **선행** 0b, 0c, G1 **저장점** `phase-1-read-api`

### Phase 2: 대시보드 설문 영역

**만드는 것**
- A-3의 설문 부분(비가중 집계, 합성 라벨, `scope: common`), S-1·S-2 화면 골격(제품군 선택, 회차 선택, 설문 집계 영역). VOC 영역은 자리만 둔다.

**완료 확인 기준** (브라우저에서)
1. 제품군과 회차를 고르면 설문 결과가 나오고 "합성" 라벨이 보인다.
2. 제품군을 바꿔도 설문 결과가 같고 "제품군과 무관" 표시가 있다(spec.md SQ-5 기본안).
3. 회차를 바꾸면 설문 결과가 바뀐다(회차가 둘 이상일 때).
4. 한 문항의 한 선택지에서 화면의 건수가 Table Editor의 `survey_answer`에서 직접 센 건수와 같다.

**예상 소요** 6시간(가정) **선행** 1 **저장점** `phase-2-dashboard-survey`

### Phase 3: 광고성 판정과 파일럿

**만드는 것**
- OpenAI 호출 모듈(키는 `backend/.env`에서만), 호출 A(광고성 판정), 규칙(G3), 출력 검증과 재시도(spec.md 6.3절).
- `ad_judgement`, `pipeline_run`, `llm_call_log` 테이블과 A-8(`ad-judgement` 단계), A-9.
- 파일럿: 판정 결과를 골든셋과 비교한 측정값 보고와 가중치 하한 결정(prd.md Q-7).

**완료 확인 기준**
1. `/docs`에서 `POST /api/rounds/{round_id}/pipeline/ad-judgement`를 실행하면 201과 `run_id`가 오고, `GET /api/runs/{run_id}`의 상태가 `succeeded` 또는 `partial`이다.
2. `counters`의 `skipped`가 992건이다(제목·본문이 모두 없는 글, 실측). 판정 대상은 310건이다.
3. Table Editor의 `ad_judgement`에서 `ad_probability`가 모두 0 이상 1 이하이고, `status`가 `ok`, `failed`, `skipped`로만 구성된다.
4. `llm_call_log`에 호출 기록이 있고 토큰 합계로 비용을 어림할 수 있다.
5. 로그 파일을 검색하면 API 키와 리뷰 본문이 없다.
6. 파일럿 결과표에 측정값(정밀도·재현율 등)이 적혀 있다. 목표값은 없고 측정값만 보고한다(prd.md 8절).
7. 가중치 하한 값이 기록되어 있다.

**예상 소요** 10시간(가정). 골든셋 라벨링 같은 사람 작업은 포함하지 않았다 **선행** 0b, G3 **저장점** `phase-3-ad-judgement-pilot`

### Phase 4: VOC 집계, 가중 토글, 판정 불가

**만드는 것**
- A-3의 VOC 부분: 비가중·가중 집계(판정에 성공한 글만), 하한 적용, `voc.counts`, `voc.undetermined`(P-5).
- S-2의 VOC 영역, 가중/비가중 토글, "판정 불가" 섹션.

**완료 확인 기준** (브라우저에서)
1. 토글을 바꾸면 VOC 집계 값이 바뀌고 설문 영역은 그대로다.
2. "판정 불가" 건수가 992건과 판정 실패 건수의 합이다. 실패가 0이면 평점 분포가 5점 895 / 4점 67 / 3점 19 / 2점 3 / 1점 8이다 (실측).
3. 판정 불가 섹션의 값이 토글과 무관하게 항상 같다.
4. VOC의 전체 건수가 선택한 제품군의 상품 건수 합과 같다(예: 상품 3개를 모두 고르면 1,302).
5. 가중 합계가 Table Editor의 `ad_judgement`에서 직접 더한 값과 같다.

**예상 소요** 8시간(가정) **선행** 2, 3, G4 **저장점** `phase-4-voc-weighted`

### Phase 5: 분석 스냅샷, 액션 제안, 근거

**만드는 것**
- 분석 스냅샷 계산·저장, 호출 B(액션 제안 서술), 검증(`row_ids`, 문장 속 숫자 일치).
- 근거를 코드가 붙이는 로직(SP-3), 근거가 없는 문장 제외(FR-2.4).
- A-10(근거 목록, 페이지 단위), S-3(근거 뷰어), S-4의 액션플랜 부분.

**완료 확인 기준** (브라우저와 Table Editor에서)
1. `action-suggestions` 단계를 실행하면 제안 문장 목록이 나오고 문장마다 근거 건수가 보인다.
2. 근거 건수를 누르면 목록이 한 쪽에 `page_size` 건씩 나뉘어 열리고, 항목을 누르면 근거 뷰어가 열린다. 뷰어에 작성자가 없다.
3. 한 문장의 근거 건수가 스냅샷의 해당 행에 들어간 응답·리뷰 수와 같다.
4. 제안 문장 속 숫자 세 개를 골라 스냅샷 값과 직접 비교하면 같다.
5. 실행 기록의 `counters`에 근거가 없어 제외된 문장 수가 기록된다.

**예상 소요** 12시간(가정) **선행** 4 **저장점** `phase-5-suggestions-evidence`

### Phase 6: 문항 초안, 리포트, 내보내기 (폐루프 완주)

**만드는 것**
- 가설 저장(G5에서 정한 방식), 호출 C(다음 회차 문항 초안), 리포트 조립(`report`, `next_survey_question`).
- A-5, A-6, A-7(독립형 HTML 내보내기), S-4 완성.

**완료 확인 기준**
1. 한 회차를 단계 순서(광고성 판정 → 스냅샷 → 액션 제안 → 문항 초안 → 리포트)대로 호출하면 리포트 화면에 액션플랜과 다음 회차 설문지가 함께 나온다.
2. 다음 회차 설문지에 "초안" 표시가 있고, Table Editor의 `next_survey_question.status`가 모두 `draft`다.
3. 문항마다 어느 가설에서 나왔는지 `hypothesis_id`로 연결된다.
4. 내보내기를 누르면 HTML 파일 하나가 저장되고, 인터넷과 시스템 접속 없이 더블클릭으로 열린다.
5. 파일에는 근거가 건수로만 적혀 있다(spec.md SQ-14 기본안).
6. 문항 → 취합 → 분석 → 액션플랜 → 다음 문항이 한 번 완주하고 회차 리포트가 출력된다(prd.md 8절, 노션 Phase 6의 확인 기준).

**예상 소요** 12시간(가정) **선행** 5, G5 **저장점** `phase-6-closed-loop`

### Phase 7: n8n 정기 실행 연결 (컷 후보)

**만드는 것**
- 단계 호출 워크플로(`backend/n8n/`), 스케줄 설정값, 내보낸 JSON.

**완료 확인 기준** (n8n 화면과 Table Editor에서)
1. 워크플로를 수동 실행하면 5개 단계가 순서대로 성공으로 표시되고 리포트가 만들어진다.
2. `pipeline_run`에 단계별 기록이 `succeeded`로 남는다.
3. 한 단계를 일부러 실패시키면(예: 잘못된 값) 워크플로가 실패로 끝나고 실행 기록이 `failed`다.
4. 내보낸 JSON을 열어 검색하면 자격 증명과 키 문자열이 없다.
5. 스케줄 값을 바꾸면 시연용으로 압축된 간격에서 실행된다.

**예상 소요** 6시간(가정) **선행** 6. 리포트 생성 실행 방식이 정해지지 않았다(prd.md Q-4) **저장점** `phase-7-n8n`

### Phase 8: 통합 점검

**만드는 것**
- prd.md 8절 통과/실패 기준 점검표, 보안·오류 점검, 반복 실행 일치율 측정.

**완료 확인 기준** (점검표에 모두 체크)
1. prd.md 8절의 통과/실패 기준 9개를 하나씩 확인해 모두 통과한다. 실패는 원인과 함께 목록으로 남긴다.
2. 같은 입력으로 같은 단계를 여러 번 실행해 반복 실행 일치율을 보고한다. 횟수는 3회(가정)이고 목표값은 없다.
3. 오류 응답 400·404·422·500이 같은 형식으로 나온다.
4. 보안 점검: `.env`가 추적되지 않고, 응답과 DB에 `author`가 없으며, 로그에 리뷰 본문과 키가 없고, 합성 응답이 모든 화면에서 "합성"으로 보인다.
5. 테스트(SQLite)가 전부 통과하고, 같은 마이그레이션을 적용한 Supabase에서도 주요 조회(대시보드, 근거 목록, 리포트)의 결과가 테스트와 같다. SQLite에서만 통과하는 문제를 막기 위한 것이다(설계 제안).
**예상 소요** 6시간(가정) **선행** 6, 7 **저장점** `phase-8-integration`

### 5.5 시간 추정의 기준: 병기 유지와 실측 보정

두 추정을 **병기**하기로 했다(PQ-8). 둘 다 근거가 약한 가정이라 어느 쪽도 정답으로 고르지 않는다. 사용자 추정(52시간)은 AI 도구 사용을 반영했는지 확인되지 않았고, 이 문서의 추정(99시간)은 AI 도구를 반영하지 않은 값이다.

**보정 방법**
1. Phase 0a(환경)와 0b(리뷰 적재)를 끝내고 실제 걸린 시간을 기록한다. 작업이 단순해서 추정 오차가 작은 Phase다.
2. 11/2 저녁 점검에서 이 실측이 두 추정 중 어느 쪽에 가까운지 보고 계수를 정한다.
3. 그 결과로 컷을 확정한다. **그 전까지 6절의 컷은 후보로만 둔다.**

| Phase | 사용자 추정 | 이 문서 추정 | 실측 | 비고 |
| --- | --- | --- | --- | --- |
| 0a 환경 준비 | 3시간(노션 Phase 1, n8n 연결 확인 포함) | 4시간 | (기록 예정) | 사용자 추정에는 n8n 연결 확인이 들어 있어 범위가 같지 않다 |
| 0b 리뷰 적재 | 3시간(노션 Phase 0) | 4시간 | (기록 예정) | |

**한계** 두 추정이 가장 크게 다른 구간은 폐루프와 대시보드(사용자 14시간, 이 문서 43시간)인데, 0a·0b는 이 구간을 대표하지 못한다. 그래서 계수를 정해도 가장 큰 구간의 오차는 남는다. 가능하면 LLM을 쓰는 Phase 3이나 화면을 만드는 Phase 2의 일부도 실측해서 확인하는 것이 안전하다 (설계 제안).

**11/2 이전에 쓸 수 있는 기준은 두 추정뿐이다.** 그래서 컷 결정도 11/2 점검 이후로 미룬다.

**축소안(승인)**: 11/2 점검은 **적재 + 광고성 판정 파일럿**까지로 줄이고, 대시보드 최소 화면은 11/3으로 넘긴다. 점검에서 보여 줄 것은 아래다.
1. Supabase Table Editor에서 `review` 1,302건 확인.
2. 100건 파일럿의 판정 결과(가정, 노션의 파일럿 규모)와, 그 결과로 계산한 가중·비가중 평균 평점의 차이 한 줄. 이 한 줄은 대시보드(Phase 4) 없이 파일럿 결과표에 넣을 수 있다(약 1시간, 가정).

이 제안은 노션 일정표의 11/2 "대시보드 최소"를 11/3으로 미루는 일정 변경이다. 또 노션의 "분류 파일럿"은 주제 분류를 가리킬 수 있는데 주제·감성 분류는 MVP 범위 밖이다(prd.md Q-15). 이 점검에서는 광고성 판정 파일럿만 보여 줄 수 있다(확인 필요 PQ-12).

**11/2 점검까지 끝나 있어야 하는 것**
- Phase 0a와 0b를 오늘 시작해도 된다. 어느 안을 택해도 필요한 작업이다.
- Supabase 프로젝트와 `DATABASE_URL` (PQ-9): 0a의 선행이다.
- 결정 게이트 G3 (2시간, 가정): 광고성 확률 결합 방식(spec.md SQ-3), OpenAI 키 점검과 모델, 비용 기준. 이것이 11/2 범위의 유일한 게이트다. G1(제품군), G2(합성 규모·회차), G4(VOC 지표), G5(가설)는 11/3 이후 Phase를 위한 것이라 11/2 점검에는 필요 없다.

### 6.3 폐루프 후반 컷의 충돌

"폐루프 후반(합성 응답 연결)을 설계 설명으로 대체"하면 아래 기준이 바뀐다.
- prd.md 8절과 mvp.md 6절의 **전체 흐름 기준**: "문항 → 취합 → 분석 → 액션플랜 → 다음 문항이 한 번 완주하고 회차 리포트가 출력된다"(노션 Phase 6의 확인 기준).
- 이 기준은 MVP의 핵심 주장(폐루프를 닫는다)이다. 설계 설명으로 대체하면 시연에서 "닫히는 것"을 보여 줄 수 없다.
- 컷하려면 PRD의 성공 기준을 고치는 결정이 필요하다. 그래서 다른 컷으로 먼저 시간을 줄이고, 이 컷은 마지막으로 두는 것을 제안한다.
