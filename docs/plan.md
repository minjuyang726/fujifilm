# 구현 계획 (Plan)

한국후지필름형 정기 설문 폐루프 에이전트의 구현 계획입니다. 범위의 근거는 [mvp.md](mvp.md), 요구사항은 [prd.md](prd.md), 구현 계약은 [spec.md](spec.md)입니다. 이 문서에는 코드가 없고, 단계(Phase)별로 무엇을 만들고 어떻게 확인하는지만 적었습니다.

## 표기 규칙

| 표기 | 의미 |
| --- | --- |
| 결정 | 사용자가 정했거나 prd.md·spec.md에서 이미 결정된 내용 |
| 가정 | 계획을 위해 둔 값. 출처 없음 |
| 설계 제안 | 승인 전까지 확정이 아닌 제안 |
| 확인 필요 | 값이나 사실을 모르는 항목. 7절 목록에 PQ 번호로 모았다 |
| 실측 | 실제 데이터에서 센 값 |

- 이 문서의 소요 시간은 모두 **가정**입니다. 근거가 없고, AI 도구 사용을 반영하지 않은 1인 작업 시간(시간 단위)입니다. 사용자가 AI 도구 기준으로 세운 별도 추정이 있고 5절에서 비교합니다(확인 필요 PQ-8).
- Git 저장점은 태그 이름으로 적었습니다. 이 프로젝트는 아직 git 저장소가 아니라서 Phase 0a에서 저장소를 만듭니다. 저장점은 사용자가 요청할 때만 만들고, 요청 없이 커밋하지 않습니다.
- 확인 방법은 브라우저와 Supabase 화면, 터미널에서 사용자가 직접 할 수 있는 것만 적었습니다.

## 1. 전제와 Phase 번호

- Phase 번호는 prd.md와 spec.md가 인용한 노션의 번호에 맞췄습니다: **Phase 0**은 데이터 적재, **Phase 3**은 광고성 판정 파일럿, **Phase 6**은 폐루프 한 번 완주(회차 리포트 출력). 나머지 번호(1, 2, 4, 5, 7, 8, 9)는 이 문서에서 새로 붙였습니다. 사용자가 전달한 노션 Phase(5.2절)와 번호와 내용이 다릅니다. 예를 들어 노션 Phase 7은 대시보드·근거 뷰어·검증 페이지이고, 이 문서의 Phase 7은 n8n 연결입니다(확인 필요 PQ-3).
- 데이터 적재는 Phase 0a(환경), 0b(리뷰), 0c(설문과 합성 응답), 0d(네이버 글)로 쪼갰습니다.
- 담당자 업로드 화면과 사람 검토 단계는 MVP에서 제외했으므로(prd.md 7절) 계획에도 없습니다.
- SP-1(`GET /api/health`)은 승인 대기라 계획에 넣지 않았습니다. 서버 확인은 FastAPI의 `/docs` 화면으로 합니다.

## 4. Phase 상세

### Phase 0a: 환경 준비

**만드는 것**
- git 저장소 초기화. `.gitignore`에 `database/data/`(원본 CSV·합성 응답 결과)를 추가한다(spec.md SQ-11, 결정).
- backend 골격: FastAPI 실행, 환경 값 읽기, `.env.example`.
- frontend 골격: Vite + React(JavaScript)가 5173 포트에서 열림.
- SQLAlchemy + Alembic 설정(spec.md 1절, 결정), psycopg 3, `backend/.venv`, pytest 1개.
- Supabase 연결(`DATABASE_URL`, session pooler 방식).

**완료 확인 기준**
1. backend 서버를 켜고 브라우저에서 `http://localhost:8000/docs`가 열린다.
2. frontend를 켜고 브라우저에서 `http://localhost:5173`이 열린다.
3. 터미널에서 pytest를 실행하면 전부 통과한다(SQLite로 돈다).
4. DB 접속 확인을 실행하면 Supabase에 연결됐다는 결과가 나온다.
5. `git status`에 `.env`는 보이지 않고 `.env.example`은 보인다.

**예상 소요** 4시간(가정) **선행** 없음. Supabase 프로젝트와 `DATABASE_URL`이 준비되어 있어야 한다(확인 필요 PQ-9) **저장점** `phase-0a-scaffold`

**확인 결과** (2026-11-01, 구현 후 직접 실행)
1. `uvicorn`으로 켜서 `http://localhost:8000/docs`가 HTTP 200으로 열렸다. `/openapi.json`도 200이고, 5173에서 오는 요청에 CORS 허용 헤더가 붙는다.
2. `npm run dev`로 켜서 `http://localhost:5173/`이 HTTP 200으로 열렸다. `npm run build`와 `npm run lint`도 통과했다.
3. `pytest`가 3개 모두 통과했다(SQLite). 경고 1건이 있다: starlette가 httpx 대신 httpx2 설치를 권장한다. 동작에는 영향이 없다.
4. **Supabase 연결은 아직 확인하지 못했다.** `DATABASE_URL`이 없을 때 실패 메시지가 나오는 것만 확인했다. 사용자가 `backend/.env`를 채운 뒤 `backend` 폴더에서 `python scripts/check_db.py`를 실행해 결과를 알려 줘야 한다.
5. `git status`에 `.env`는 없고 `backend/.env.example`, `frontend/.env.example`은 추적 대상으로 보인다. `backend/.env`, `frontend/.env`, 가상환경, `node_modules`, `dist`, `__pycache__`, `.pytest_cache`는 모두 무시된다.

**갱신 (2026-11-01)**: 완료 확인 기준 1~5가 모두 통과했다. 기준 4(Supabase 연결)는 사용자가 `backend/.env`를 채운 뒤 직접 확인했다(위 4번의 "확인하지 못했다"는 구현 시점의 기록이다).

새로 만든 파일의 키·비밀번호 패턴 검사에서 일치한 2건은 테스트에 쓴 가짜 URL(`u:p@host`)이다. 실제 소요 시간은 사용자가 기록해 5.5절 보정 표에 넣는다.

### Phase 0b: 리뷰 적재

**만드는 것**
- `product`, `review` 테이블(spec.md 3.2절)과 마이그레이션. `product.family_id`와 `product_family` 테이블은 제품군 목록이 정해지는 Phase 1(G1)에서 추가한다.
- 쿠팡 CSV(`database/data/`에 복사해 둔 파일)를 읽어 적재하는 스크립트. `author`, `seller`, `source_file`, `original_no`는 읽지 않고, 빈 문자열은 NULL로 바꾼다(spec.md 3.1절).

**완료 확인 기준** (Supabase의 Table Editor에서)
1. `review` 행이 1,302개, `product` 행이 3개다.
2. `title`이 NULL인 행이 1,152개, `review_text`가 NULL인 행이 1,005개, `variant`에 값이 있는 행이 351개다 (모두 실측).
3. `rating`별 건수가 5점 1,164 / 4점 91 / 3점 25 / 2점 4 / 1점 18이다 (실측).
4. `review_id`의 최솟값이 1043, 최댓값이 2344다 (실측).
5. `review` 테이블에 `author` 열이 없다.
6. 적재 스크립트를 두 번 실행해도 `review` 행이 1,302개로 그대로다.

**예상 소요** 4시간(가정) **선행** 0a **저장점** `phase-0b-reviews-loaded`

**확인 결과** (2026-11-01, 임시 SQLite 파일에서 직접 실행. Supabase에는 아직 쓰지 않았다)
- 마이그레이션 `0001`이 적용됐고 `alembic check`가 "변경 없음"이었다(모델과 마이그레이션이 같다).
- 실제 CSV를 적재한 뒤 값이 기준 1~4와 모두 일치했다: `review` 1,302행, `product` 3행, `title` NULL 1,152, `review_text` NULL 1,005, `variant` 값 있음 351, 평점 5점 1,164 / 4점 91 / 3점 25 / 2점 4 / 1점 18, `review_id` 1043~2344 (모두 실측).
- 같은 CSV를 한 번 더 적재해도 행 수가 그대로였다(기준 6). 빈 문자열로 남은 값은 0개다.
- `review` 테이블에 `author` 열이 없다(기준 5). pytest는 11개 통과했다(SQLite).
- 적재 스크립트가 출력하는 "대상 DB"는 `sqlite`였다. 이 확인에서 Supabase에는 접속하지 않았다.

**갱신 (2026-11-01)**: Supabase에서 완료 확인 기준 1~6이 모두 통과했다. 기준 6(두 번 실행해도 1,302행)은 적재 스크립트를 두 번 실행해 확인했다. 위 "확인 결과"는 구현 시점의 SQLite 기록이다.

**Supabase에서 사용자가 확인할 순서** (`backend` 폴더에서, `.env`에 `DATABASE_URL`이 있어야 한다)
1. `alembic upgrade head`
2. `python scripts/load_reviews.py` — 출력에 "대상 DB: postgresql"이 보이는지, "DB에 들어 있는 값"의 숫자가 위와 같은지 본다.
3. Table Editor에서 기준 1~5를 확인한다.
4. 스크립트를 한 번 더 실행해 `review`가 1,302행 그대로인지 본다(기준 6).

### Phase 0c: 설문 구조와 합성 응답 적재

**만드는 것**
- `survey_question`, `survey_response`, `survey_answer` 테이블. (`round`는 Phase 3 마이그레이션 `2c6efdf1a38e`에서 이미 만들었다.)

### Phase 5: 분석 스냅샷, 액션 제안, 근거

**만드는 것**

**완료 확인 기준** (브라우저와 Table Editor에서)
1. `action-suggestions` 단계를 실행하면 제안 문장 목록이 나오고 문장마다 근거 건수가 보인다.

### Phase 6: 문항 초안, 리포트, 내보내기 (폐루프 완주)

**만드는 것**
- 가설 저장(G5에서 정한 방식), 호출 C(다음 회차 문항 초안), 리포트 조립(`report`, `next_survey_question`).
- A-5, A-6, A-7(독립형 HTML 내보내기), S-4 완성.

**완료 확인 기준**
1. 한 회차를 단계 순서(광고성 판정 → 스냅샷 → 액션 제안 → 문항 초안 → 리포트)대로 호출하면 리포트 화면에 액션플랜과 다음 회차 설문지가 함께 나온다.
2. 다음 회차 설문지에 "초안" 표시가 있고, Table Editor의 `next_survey_question.status`가 모두 `draft`다.
3. 문항마다 어느 가설에서 나왔는지 `hypothesis_id`로 연결된다.
4. 내보내기를 누르면 HTML 파일 하나가 저장되고, 인터넷과 시스템 접속 없이 더블클릭으로 열린다.
5. 파일에는 근거가 건수로만 적혀 있다(spec.md SQ-14 기본안).
6. 문항 → 취합 → 분석 → 액션플랜 → 다음 문항이 한 번 완주하고 회차 리포트가 출력된다(prd.md 8절, 노션 Phase 6의 확인 기준).

**예상 소요** 12시간(가정) **선행** 5, G5 **저장점** `phase-6-closed-loop`

### Phase 7: n8n 정기 실행 연결 (컷 후보)

**만드는 것**

**완료 확인 기준** (n8n 화면과 Table Editor에서)

**예상 소요** 6시간(가정) **선행** 6. 리포트 생성 실행 방식이 정해지지 않았다(prd.md Q-4) **저장점** `phase-7-n8n`

### 5.5 시간 추정의 기준: 병기 유지와 실측 보정

3. 그 결과로 컷을 확정한다. **그 전까지 6절의 컷은 후보로만 둔다.**
