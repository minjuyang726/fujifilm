# PRD (제품 요구사항)

한국후지필름형 정기 설문 폐루프 에이전트의 제품 요구사항 문서입니다. 범위의 근거는 [mvp.md](mvp.md)이고, 그 근거는 [service-definition.md](service-definition.md)입니다. 이 문서에서 mvp.md에 없는 기능을 요구사항으로 추가하지 않았습니다. 추가가 필요해 보이는 것은 9절 "제안"에 따로 모았고, 승인 전까지 요구사항이 아닙니다.

## 표기 규칙

표기 규칙은 service-definition.md와 mvp.md를 따릅니다(결정, 가정, 설계 제안, 미정). 이 문서에서 더하는 표기는 아래와 같습니다.

| 표기 | 의미 |
| --- | --- |
| 확인 필요 | 값이나 사실을 모르는 항목. 10절 목록에 번호로 모았다 |
| 제안 | mvp.md에 없지만 필요해 보여 따로 분리한 항목. 승인 전까지 요구사항이 아니다 |

- 수치에는 실측/가정/합성 중 하나를 붙입니다. 합성 응답에서 나온 수치는 성과로 쓰지 않습니다.
- 요구사항 번호는 기능 요구사항(FR), 비기능 요구사항(NFR)으로 붙입니다.

## 1. 배경과 목표

### 배경 (가정)

정기 설문을 운영하는 CX 담당자는 회차마다 설문지를 만들고, 응답과 외부 고객 목소리(VOC)를 따로 분석하고, 제안의 근거를 일일이 찾아 보고서를 씁니다. 분석에서 남은 의문은 다음 회차 문항으로 이어지는지가 담당자 기억에 달려 있습니다.

위 내용은 모두 가정입니다. 일반적인 소비재 기업의 정기 설문 운영을 가정한 흐름이며, 후지필름에서 확인된 사실이 아닙니다. 실제 운영 방식은 본선 자료로 확인합니다(확인 필요 Q-1).

### 목표 (결정)

- 설문과 VOC를 제품군별로 결합해 대시보드에 보여준다.
- 액션 제안마다 근거 응답을 추적할 수 있게 한다.
- 액션플랜과 다음 회차 설문지를 담은 회차 리포트를 내보내, 분석에서 남은 의문이 다음 회차로 이어지는 폐루프를 한 번 완주한다.

## 2. 사용자와 시나리오

### 사용자

| 사용자 | 하는 일 | 표기 |
| --- | --- | --- |
| CX 담당자 | 대시보드와 근거 뷰어를 직접 쓰고, 회차 리포트를 내보낸다 | 결정(과제를 가정한 페르소나이며 실제 사용자 조사는 아님) |
| 의사결정자(팀장·임원) | 시스템을 쓰지 않고, 내보낸 회차 리포트만 받는다 | 가정 |

- 소규모 CX 팀이 제품군을 나눠 맡거나 겸임한다. 한 사람이 여러 제품군을 볼 수 있다. (가정, 확인 필요 Q-1)
- 회차 주기는 분기 단위로 가정한다. 근거는 없다. (가정, 확인 필요 Q-1)

### 시나리오

시나리오는 mvp.md의 기능을 담당자 관점에서 이어 붙인 것입니다.

1. **결과 확인**: 담당자가 제품군을 고르고 설문 집계와 외부 VOC가 결합된 결과를 본다. 회차를 바꿔 문항 결과를 보고, VOC의 가중/비가중을 전환해 비교한다. (FR-1.x)
2. **근거 확인**: 담당자가 액션 제안을 읽다가 근거 ID를 선택해 원래 응답이나 리뷰를 근거 뷰어에서 확인한다. (FR-2.x)
3. **리포트 내보내기**: 담당자가 액션플랜과 다음 회차 설문지가 담긴 회차 리포트를 내보낸다. 내보낸 리포트를 의사결정자에게 전달하는 일은 시스템 밖의 수작업이다. (FR-3.x)

응답 데이터는 담당자가 올리지 않고 개발 초기 단계(Phase 0)에서 스크립트로 적재되어 있다고 전제합니다(mvp.md 5절).

## 3. 기능 요구사항

각 요구사항의 출처는 mvp.md의 절입니다.

### 공통 원칙: 계산은 코드가, 서술은 LLM이 한다

| 번호 | 요구사항 | 출처 |
| --- | --- | --- |
| FR-0.1 | 집계, 비율, 가중치 계산, 비교 같은 모든 계산은 코드가 한다 | 결정(원칙) |
| FR-0.2 | LLM은 코드가 계산한 표만 입력받아 서술한다(액션 제안 문장, 다음 회차 문항 초안). LLM이 수치를 새로 만들거나 바꾸지 않는다 | 결정(원칙), service-definition.md 2절 |
| FR-0.3 | 서술에 나오는 수치는 코드가 계산한 표의 값과 일치해야 한다 | FR-0.2에서 도출 |
| FR-0.4 | 광고성 판정에서 LLM은 광고성 확률을 내는 데에만 쓰고, 그 확률로 가중치를 계산하고 집계하는 일은 코드가 한다 | mvp.md 4절 |

### 기능 1. 제품군별 결과 확인 (mvp.md 4절, 행동 3)

| 번호 | 요구사항 | 비고 |
| --- | --- | --- |
| FR-1.1 | 담당자는 제품군을 고를 수 있다 | 제품군 목록은 미정(확인 필요 Q-3) |
| FR-1.2 | 제품군을 고르면 설문 집계와 외부 VOC가 결합된 결과가 한 화면에 나온다 | |
| FR-1.3 | 담당자는 회차를 골라 해당 회차의 문항 결과를 볼 수 있다 | 시연 회차 수는 미정(확인 필요 Q-6) |
| FR-1.4 | 외부 VOC에 대해 LLM으로 광고성 확률(0~1)을 판정한다. 규칙 신호는 파일럿에서 LLM 단독 결과와 골든셋을 본 뒤에 추가할지 정한다(SQ-3 결정 A, 2026-11-02) | FR-0.4 적용 |
| FR-1.5 | 광고성 가중치 = 1 − 광고성 확률(0~1)로 계산한다 | 결정 |
| FR-1.6 | 광고성으로 판정된 글은 삭제하지 않고 가중만 낮춘다 | 결정 |
| FR-1.7 | 가중치에는 하한(최소값)이 있다 | 하한 값은 파일럿에서 정함(확인 필요 Q-7) |
| FR-1.8 | 담당자는 외부 VOC 집계를 가중/비가중 토글로 전환해 볼 수 있고, 가중 집계와 비가중 집계를 모두 볼 수 있다 | 결정 |
| FR-1.9 | 설문 응답 집계는 토글과 무관하게 비가중으로 집계한다 | KOSSDA 두 자료에 가중치 변수 없음 |
| FR-1.10 | 합성 응답에는 "합성" 라벨이 고정으로 붙어 화면에 보인다 | 결정 |
| FR-1.11 | 광고성 판정 대상은 제목이나 본문이 있는 글이다(310건, 실측). (3-2) 해결 전에는 표본 100건만 판정한다(PQ-13 결정, 2026-11-02). 화면은 건수와 평점 분포를 세 묶음으로 보인다. **판정**: 판정에 성공한 글. **미판정**: 판정 대상이지만 판정하지 않았거나(표본 밖) 판정에 실패한 글. **제목·본문 없음**: 제목·본문이 모두 없는 글(992건, 실측). 가중/비가중 토글은 '판정' 묶음에만 적용되고, '미판정'과 '제목·본문 없음'은 토글과 무관하게 S-2의 별도 섹션에 건수와 평점 분포만 표시한다 | 제안 P-5를 승인해 반영함(표기는 PQ-13 결정으로 "판정 불가"를 '미판정'과 '제목·본문 없음'으로 나눔, 2026-11-02). '제목·본문 없음'의 평점 분포는 5점 895, 4점 67, 3점 19, 2점 3, 1점 8건(실측) |

### 기능 2. 근거 추적 (mvp.md 4절, 행동 4)

| 번호 | 요구사항 | 비고 |
| --- | --- | --- |
| FR-2.1 | 액션 제안마다 근거 ID가 연결된다 | |
| FR-2.2 | 담당자가 근거 ID를 선택하면 해당 근거 응답(또는 리뷰)이 근거 뷰어에 열린다 | |
| FR-2.3 | 모든 제안 문장이 근거 ID를 가진다 | 처리 규칙은 FR-2.4 |
| FR-2.4 | 서술이 끝난 뒤 코드가 제안 문장마다 근거 ID 유무를 검사하고, 근거 ID가 없는 문장은 리포트에 담지 않는다 | 제안 P-2를 승인해 반영함. 제안이 거의 남지 않는 경우의 처리는 확인 필요 Q-16 |
| FR-2.5 | 근거 뷰어는 리뷰 근거에 대해 review_id, 평점, 날짜, 본문만 보여주고 작성자(author)는 보여주지 않는다 | 제안 P-4를 승인해 반영함 |
| FR-2.6 | 제안 문장의 근거는 그 문장이 참조한 집계 행에 들어간 모든 응답·리뷰이며, 코드가 붙인다. LLM은 근거 ID를 고르지 않는다 | spec.md의 제안 SP-3를 승인해 반영함. 문장 하나에 근거가 수백~천 건 붙을 수 있어 근거는 목록(페이지 단위)으로 본다 |

### 기능 3. 회차 리포트 내보내기 (mvp.md 4절, 행동 6)

| 번호 | 요구사항 | 비고 |
| --- | --- | --- |
| FR-3.1 | 회차 리포트에는 액션플랜과 다음 회차 설문지가 함께 담긴다 | |
| FR-3.2 | 이전 회차의 불확실·모순 가설로 다음 회차 문항 초안을 만든다 | 가설을 가려내는 방식은 정해지지 않았고, 가려내는 단계에 LLM이 어디까지 관여할지도 미정이다(확인 필요 Q-5) |
| FR-3.3 | 다음 회차 설문지는 초안 상태로 리포트에 담긴다 | 담당자 확정 단계 없음 |
| FR-3.4 | 시스템이 만든 액션 제안이 담당자의 수정 없이 그대로 리포트에 담긴다 | 담당자 선별·수정 단계 없음 |
| FR-3.5 | 담당자는 회차 리포트를 내보낼 수 있다. 시스템은 내보내기까지만 맡는다 | 내보내기 형식은 미정(확인 필요 Q-8) |
| FR-3.6 | 회차 리포트를 만드는 실행 방식은 미정이다 | 설계에는 n8n이 회차별 정기 실행과 단계 연결을 맡는 것으로 적혀 있으나, 리포트 생성의 실행 방식으로 확정된 것은 아니다(확인 필요 Q-4) |

### 입력 데이터

| 데이터 | 내용 | 표기 / 상태 |
| --- | --- | --- |
| 쿠팡 후지필름 리뷰 CSV | 총 1,302건(QuickSnap 541, mini EVO 410, MINI12 351). 텍스트가 있는 리뷰는 297건 | 실측 |
| 네이버 블로그·카페 글 | 텍스트 부족을 보강하는 외부 VOC. 수집은 진행 전 | 건수 확인 필요 Q-2 |
| KOSSDA 자료 15683(주), 14488(보조) | 설문 응답 구조를 따르기 위한 참고 자료 | 자료 번호이며 수치 아님 |
| 합성 응답 | KOSSDA 구조를 따라 만든 응답 | 합성, 건수 확인 필요 Q-6 |

### 데이터 요구사항

| 번호 | 요구사항 |
| --- | --- |
| DR-1 | 설문 응답은 KOSSDA 구조를 따른 표준화된 구조로 적재한다. 적재는 Phase 0에서 스크립트로 한다 |
| DR-2 | 합성 응답은 실제 응답과 구분되는 "합성" 표시를 데이터에 고정으로 갖는다 |
| DR-3 | 외부 VOC 글마다 광고성 확률과 가중치를 저장한다. 글은 삭제하지 않는다 |
| DR-4 | 모든 응답과 리뷰는 근거 ID로 식별되고, 근거 ID로 원문에 되돌아갈 수 있다 |
| DR-5 | 데이터는 회차와 제품군(미정)으로 구분할 수 있어야 한다 |
| DR-6 | 쿠팡 CSV는 상품 3개 단위이며, 상품과 제품군의 대응은 제품군 사전 작업에서 확정한다(제안: 일회용 카메라 1개 + 인스탁스 즉석카메라 2개 상품. 설계 제안. 2026-11-02 채택, G1 결정) |

### 확인 필요한 데이터 사항

- 쿠팡 CSV의 열 구성 (실측, 직접 열어 확인): 12개 열, 1,302행.
  - 열: review_id, product_name, source_file, original_no, rating, date, author, seller, variant, helpful_count, title, review_text
  - author 열: 1,302행 모두에 값이 있고 고유값은 903개다. 1,096건(약 84%)은 *가 들어 있고, 그중 1,021건은 성 + * + 끝 글자 형태다(실측, 직접 집계). 나머지에는 가려지지 않은 닉네임으로 보이는 값과 OO로 가린 값이 섞여 있다. 이름 일부 또는 닉네임이므로 개인 식별 정보가 아니라고 단정할 수 없다.
  - seller 열: 값이 모두 비어 있다(고유값 0개).
  - 본문(title, review_text)의 개인정보 패턴 (실측, 직접 집계): 전화번호·이메일·URL 패턴은 0건이다. 이름은 패턴으로 찾을 수 없어 확인하지 못했다 (확인 필요 Q-10)
  - 본문(review_text)이 있는 리뷰 297건의 상품별 분포 (실측): QuickSnap 188, mini EVO 57, MINI12 52. 제목이나 본문이 있는 리뷰는 310건이고, 둘 다 빈 리뷰는 992건이다
  - 평점 분포 (실측): 5점 1,164건(약 89%), 4점 91, 3점 25, 2점 4, 1점 18. 1~2점은 합쳐서 22건뿐이다

## 9. 제안 (승인 대기)

아래는 mvp.md에 없지만 필요해 보여 분리한 항목입니다. 승인 전까지 요구사항이 아니며, 승인된 제안만 요구사항 표로 옮기고 상태에 "승인"을 적습니다.

| 번호 | 제안 | 이유 | 승인 시 영향 |
| --- | --- | --- | --- |
| P-1 | 근거 뷰어에 근거 글의 광고성 확률과 가중치를 함께 표시한다 | 가중/비가중 차이가 어떤 글 때문인지 담당자가 확인할 수 있다 | 기능 2의 화면 요소가 늘어난다. **상태: 보류.** 광고성 확률과 가중치는 글마다 저장하므로(DR-3) 나중에 붙이는 비용이 작고, 11/2 저녁 1차 점검 전에 MVP 범위를 늘리고 싶지 않으며, 광고성 판정의 정확도는 Phase 3 파일럿 결과를 보기 전에는 알 수 없어 부정확하면 담당자에게 틀린 신호를 줄 수 있다 |
| P-2 | 근거 ID를 갖지 못한 제안 문장은 리포트에 담지 않는다 | FR-2.3("모든 제안 문장이 근거 ID를 가진다")을 지키는 방법이 정해져 있지 않다 | FR-2.3의 처리 규칙이 생긴다. **상태: 승인.** FR-2.4로 요구사항에 반영함. 새 기능이 아니라 기존 성공 기준을 지키는 규칙이고, 코드가 검사하므로 "계산은 코드가" 원칙과 맞으며, LLM이 근거를 꾸며 붙이는 것을 막는 효과도 있다. 감수할 점은 리포트의 제안 수가 줄 수 있다는 것 |
| P-3 | 적재된 데이터의 건수와 출처를 보는 확인 화면을 둔다 | 업로드 화면이 없어서 어떤 데이터가 적재됐는지 화면에서 확인할 방법이 없다 | 화면이 하나 늘어난다. **상태: 거절.** 적재 상태는 Phase 0 스크립트의 출력이나 DB에서 직접 확인한다 |
